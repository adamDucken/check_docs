### How Rustdoc JSON works with Cargo
1. **Will it generate docs for the exact version?** Yes. Because you run `cargo` within the context of the user's project, it respects their `Cargo.lock`. If they use `tokio v1.20.0`, it will generate the docs for exactly that version, exactly how their project is configured (with their specific enabled features).
2. **Can we generate docs for all crates at once, or sequentially?** You *can* do it all at once using `cargo doc`, but **you shouldn't**. Generating docs for the entire dependency tree takes a long time (minutes on large projects). 
   Instead, you should do it **on-demand (Lazy Loading)**. When an agent queries `use tokio::sync::mpsc;`, your tool should check if `target/doc/tokio.json` exists. If it doesn't, you run a command to generate the JSON *only* for `tokio`. This is very fast.

### The Plan: Moving to `rustdoc-types`

Here is a 4-step plan to transition `check-docs` from `syn` to Rustdoc JSON.

#### Step 1: Add the necessary dependencies
You no longer need `syn` or `quote` to parse file contents. Instead, you need the official crate that defines the Rustdoc JSON schema.

```toml
[dependencies]
rustdoc-types = "0.23" # Check for the latest version
cargo_metadata = "0.18"
serde = { version = "1.0", features = ["derive"] }
serde_json = "1.0"
```

#### Step 2: Generate Rustdoc JSON On-Demand
Instead of reading `.rs` files manually, you will shell out to `cargo` to generate the JSON. You will need the `nightly` toolchain because the JSON output format is an unstable feature (though it is highly reliable for tooling).

cargo +nightly rustdoc -p syn -- -Z unstable-options --output-format json
When a user asks for `crate_name::module::item`:
1. Resolve `crate_name` using `cargo_metadata` (you already do this perfectly in `resolver.rs`).
2. Run this command:
   ```bash
   cargo +nightly rustdoc -p <crate_name> -- -Z unstable-options --output-format json
   ```
3. This will compile the dependencies and generate a file at:
   `target/doc/<crate_name_with_underscores>.json`

*Note: There is a great community crate called `rustdoc-json` which automates executing this exact command from Rust code if you prefer not to use `std::process::Command` manually.*

#### Step 3: Traverse the JSON Graph Programmatically
Once the JSON is generated, load it into the `rustdoc_types::Crate` struct using `serde_json`. 

The JSON is a flat dictionary of `Id` -> `Item`. You will write a recursive function to walk this graph, which replaces your `resolve_module` and `collect_items_recursive` functions.

Here is the mental model for your new traversal logic:
1. Start at `doc.root` (The ID of the `lib.rs` root module).
2. Look up the ID in `doc.index`. It will be an `ItemEnum::Module`.
3. The module contains an array of child `Id`s. Look up each child.
4. If the user asked for `sync`, find the child where `name == "sync"`.
5. Repeat until you reach the target item.
6. **Crucial:** If you encounter an `ItemEnum::Import` (a `pub use`), you simply grab its `id` and jump to the referenced item! This completely solves your re-export nightmare.

#### Step 4: Map the JSON Item back to your `SymbolDoc`
Once you find the exact `rustdoc_types::Item`, map its structured data back into your clean CLI output.

* **Docs:** Pull directly from `item.docs`.
* **Line numbers/Location:** Pull from `item.span` (contains file path, begin line, end line).
* **Definition:** Use the structured data. For example, if it's a `Struct`, `rustdoc_types` will give you arrays of fields, generics, and bounds. You can easily format this into a string like `pub struct Config { ... }`.
* **Derives:** Can be parsed from `item.docs` or `item.attrs` (though rustdoc often processes these natively).

### What your architecture will look like

* `cli.rs`: Stays exactly the same.
* `imports.rs`: Stays exactly the same (parsing the `use` string into target segments).
* `resolver.rs`: Simplified. Still finds the crate via `cargo_metadata`, but no longer searches for `src/lib.rs`.
* `symbols.rs`: **Completely rewritten.** Replaces file system `WalkDir` and `syn` with:
  1. `Command::new("cargo").args(["+nightly", "rustdoc", ...])`
  2. `let doc: rustdoc_types::Crate = serde_json::from_reader(File::open("target/doc/tokio.json"))?;`
  3. A clean ID-graph traversal algorithm.

### Why this is a Massive Upgrade
1. **No More Macro Blindspots:** Macros are fully expanded by the compiler. If a struct is generated by `bitflags!`, rustdoc will just output standard `Struct` JSON for it. Your tool will see it exactly as if it was written by hand.
2. **Perfect Re-exports:** Glob imports (`pub use prelude::*`) and nested aliases are evaluated by the compiler. You just follow the JSON ID pointers.
3. **Zero false positives:** `syn` lossy parsing occasionally pulls in private structs or test-only mocks. Rustdoc JSON strictly understands visibility rules and `cfg` flags.

You are providing the exact right abstraction: The raw power and precision of the Rust compiler, condensed into a 150-token CLI output that an AI agent can read instantly.
